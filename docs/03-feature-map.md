# Feature Map

Priority labels:

- P0: Required for MVP/thesis demo.
- P1: Important but can be simplified if timeline is tight.
- P2: Optional or future-facing.

Status labels:

- Existing: already present in the prototype in some form.
- Partial: started but needs service-layer cleanup or completion.
- Planned: should be implemented for MVP.
- Deferred: keep out of MVP unless time allows.

| Feature | Primary Screens | Main Data Tables | Priority | Status | Notes |
| --- | --- | --- | --- | --- | --- |
| Registration | `app/(auth)/register.tsx` | `auth.users`, `profiles` | P0 | Existing | MVP signup uses Supabase email OTP plus password creation. Phone-first/SMS auth is deferred until provider access and device testing are practical. |
| Login/logout | `app/(auth)/login.tsx`, profile screen | `auth.users` | P0 | Existing | Session handled by Supabase. |
| Role selection | `app/(auth)/role.tsx` | `profiles`, `user_roles` | P0 | Existing | Client, provider, and both-role intent are supported. Both stores client and provider role rows. |
| Onboarding profile | `app/(onboarding)/*` | `profiles`, `provider_profiles`, `client_profiles`, `user_preferences` | P0 | Existing | Role intent -> basic identity/location -> service preferences -> review -> complete -> Home. Completion requires `user_preferences.onboarding_completed_at` plus basic profile identity. No certificates, ID documents, or verification uploads are collected in first onboarding. |
| Unverified viewer mode | Main tabs, locked action prompts | `profiles`, `verifications`, `user_preferences` | P0 | Partial | Users can browse after lightweight onboarding but cannot interact until verified. Provider intent opens Home on Jobs; client intent opens Services; both/missing intent opens For you. Verification unlock refresh is now connected; keep broader Home/Search scope frozen until the verified Post slice is stable. |
| Profile view/edit | `app/(tabs)/profile.tsx` | `profiles`, `provider_profiles`, `client_profiles`, `credentials`, `reviews`, jobs/services summaries | P0 | Partial | Profile is a resident identity, skills, trust, role-specific reputation, and history surface. Completion is based on profile readiness, not active listings, drafts, saved items, pricing, or budgets. |
| Service listings | Work Profile defaults, offer service screen, Post Dashboard | `services`, `service_drafts`, `provider_profiles` | P0 | Partial | Service creation, owned-service listing, drafts, and active-service search use listing-owned rates, schedules, photos, and message settings. Work Profile only provides skills/defaults for blank-draft suggestions. |
| Credential upload | `app/(onboarding)/certifications.tsx`, verification screen | `credentials`, `verification_files`, storage bucket | P0 | Partial | Verification file upload now uses Supabase Storage and `verification_files`. Camera capture for ID/selfie is a polish/hardening task; document/image picker remains acceptable for the verified Post slice. |
| Barangay verification request | `app/verification.tsx`, `components/verification/FigmaVerificationFlow.tsx`, profile settings | `verifications`, `verification_files`, `profiles`, `contact_otp_challenges` | P0 | Existing | Verification follows the established Figma storyboard and now requires a server-verified Philippine mobile OTP challenge before submission. PhilSMS delivery stays server-side; restricted simulated delivery is available for approved local test users/numbers. |
| Admin verification review | `app/admin/verifications.tsx` | `verifications`, `verification_files`, `profiles` | P0 | Existing | Barangay admins are routed to a focused verification dashboard with queue filters, request metrics, submitted profile/file details, in-app image preview, logout, and approve/reject actions through `AdminService`. It remains verification-focused, not a full moderation dashboard, and keeps current `verifications` naming for MVP. |
| Home feed | `app/(tabs)/index.tsx`, Figma dashboard | `jobs`, `services`, `profiles`, `reviews`, `saved_items` | P0 | Partial | Home now loads real open jobs and active services from Supabase, preserves intent-based default filters, uses lightweight preference scoring plus mixed `For you` ordering, has a local discovery filter sheet for feed type, work mode, category, location preference, and sort, and exposes functional save toggles for visible feed cards. |
| Job posting and management | `app/create-job.tsx`, `app/create-job-preview.tsx`, `app/(tabs)/post.tsx`, `app/post/active.tsx` | `jobs`, `job_drafts` | P0 | Existing | Post is the primary owner surface for active posts, drafts, final posts, edit actions, lifecycle actions, and completed-job review entry. Owner job detail may link to the same edit flow. Profile may show history but does not own post management. |
| Job browsing | Home/search screens, job detail | `jobs` | P0 | Partial | Providers can view open jobs. Job details are task-first, keep poster trust metrics separate from job tags, and link to a safe public client profile that exposes only public-safe identity, activity, and active-job data. `explore` is legacy and should be replaced by Home/Search. |
| Provider browsing | Home/search screens, worker detail | `profiles`, `provider_profiles`, `services`, `credentials`, `reviews` | P0 | Partial | Clients can view providers. Worker details are person-first and separate identity/trust/skills/reviews/history from marketplace inventory such as active service listings and listing rates. `explore` is legacy and should be replaced by Home/Search. |
| Job interest messaging | Messages tab, job detail, feed cards | `conversations`, `messages`, `jobs` | P0 | Existing | Job detail starts/reuses a job conversation and conversation detail supports text messages, quick prompts, job context, conversation details, report, archive, and Mark Hired. |
| Hiring management | Messages tab, job history, post dashboard | `jobs`, `conversations` | P0 | Partial | Client can mark a conversation as hired; this updates conversation status and job accepted provider/status. |
| Search and filtering | Search tab | `jobs`, `services`, `profiles` | P0 | Partial | Search is a main bottom-navigation destination for intentional job/service discovery. Services and jobs have service-layer search hooks; Home keeps lightweight feed filter pills and preference scoring. |
| Ratings and feedback | Completed job detail, conversation details, public profiles, Post management | `reviews`, `jobs`, `conversations` | P1 | Existing | Reviews are reciprocal and immutable. After a completed hired job, the client may review the accepted worker and the worker may review the client once. Database RPCs derive the counterparty and enforce completion, hired participation, verification, no self-review, and no duplicates. |
| Reports/moderation | Admin dashboard, report modal | `reports` | P1 | Planned | Basic moderation for unsafe content. |
| Basic messaging | Messages tab, `app/conversation/[conversationId].tsx` | `conversations`, `messages`, `conversation_reads`, private message storage | P0 | Existing | Real inbox, job/service conversations, text and private image messages, quick prompts, unread counts, context cards, details, report, and archive are connected. Calls, push notifications, group chat, and per-message read receipts remain deferred. |
| Saved providers/jobs | Home/Search cards | `saved_items` | P1 | Existing | Visible save/bookmark actions persist real job and provider saves for verified users, prevent duplicates, and restore state from Supabase when discovery screens regain focus. |
| Notifications | Home header, Messages header, `app/notifications.tsx` | `notifications` | P1 | Partial | Basic in-app notification center with unread/read state for messages, verification decisions, completed hired jobs, and report status changes. Push delivery and preferences remain deferred. |
