# Feature Map

Priority labels:

- P0: Required for MVP/thesis demo.
- P1: Important but can be simplified if timeline is tight.
- P2: Optional or future-facing.

Status labels:

- Existing: already present in the prototype in some form.
- Partial: started but needs service-layer cleanup or completion.
- Planned: should be implemented for MVP.
- Deferred: keep out of MVP unless time allows.

| Feature | Primary Screens | Main Data Tables | Priority | Status | Notes |
| --- | --- | --- | --- | --- | --- |
| Registration | `app/(auth)/register.tsx` | `auth.users`, `profiles` | P0 | Existing | MVP signup uses Supabase email OTP plus password creation. Mobile-number signup, login, and password recovery are built (DEC-127, DEC-131) but stay behind `EXPO_PUBLIC_PHONE_AUTH_ENABLED`, which is off until the Supabase Phone provider and the PhilSMS `send-sms-hook` are switched on (`docs/07` checklist). |
| Login/logout | `app/(auth)/login.tsx`, profile screen | `auth.users` | P0 | Existing | Session handled by Supabase. |
| Role selection | `app/(auth)/role.tsx` | `profiles`, `user_roles` | P0 | Existing | Client, provider, and both-role intent are supported. Both stores client and provider role rows. |
| Onboarding profile | `app/(onboarding)/*` | `profiles`, `provider_profiles`, `client_profiles`, `user_preferences` | P0 | Existing | Account -> profile -> identity -> review, with a 4-phase progress bar (DEC-124). Review saves the profile, then routes to `/(onboarding)/verify`, which runs barangay verification as the final phase; "Do this later" skips it and leaves a complete browse-only account. Completion requires `user_preferences.onboarding_completed_at` plus basic profile identity, not verification. |
| Unverified viewer mode | Main tabs, locked action prompts | `profiles`, `verifications`, `user_preferences` | P0 | Partial | Users can browse after onboarding but cannot interact until verified. Every gate goes through `hooks/use-verification-gate.ts` (DEC-126), which tells pending residents their request is under review instead of sending them back into verification. Provider intent opens Home on Jobs; client intent opens Services; both/missing intent opens For you. Verification unlock refresh is now connected; keep broader Home/Search scope frozen until the verified Post slice is stable. |
| Profile view/edit | `app/(tabs)/profile.tsx` | `profiles`, `provider_profiles`, `client_profiles`, `credentials`, `reviews`, jobs/services summaries | P0 | Partial | Profile is a resident identity, skills, trust, role-specific reputation, and history surface. Completion is based on profile readiness, not active listings, drafts, saved items, pricing, or budgets. |
| Service listings | Work Profile defaults, offer service screen, Post Dashboard | `services`, `service_drafts`, `provider_profiles` | P0 | Partial | Service creation, owned-service listing, drafts, and active-service search use listing-owned rates, schedules, photos, and message settings. Work Profile only provides skills/defaults for blank-draft suggestions. |
| Credential upload | `app/profile/credentials.tsx`, verification flow | `credentials`, `verification_files`, storage bucket | P0 | Partial | Professional credentials are managed from Profile; identity documents are uploaded inside the verification flow. Verification file upload uses Supabase Storage and `verification_files`. Camera capture for ID/selfie is a polish/hardening task; document/image picker remains acceptable for the verified Post slice. The onboarding certifications screen was removed with DEC-124. |
| Barangay verification request | `app/verification.tsx`, `app/(onboarding)/verify.tsx`, `components/verification/VerificationScreen.tsx`, `components/verification/FigmaVerificationFlow.tsx`, profile settings | `verifications`, `verification_files`, `profiles`, `contact_otp_challenges` | P0 | Existing | One controller (`VerificationScreen`) runs standalone and as the last onboarding phase (DEC-124). Verification follows the established Figma storyboard, requires a server-verified Philippine mobile OTP challenge before submission, and shows the real review status afterwards instead of simulated checks (DEC-125). PhilSMS delivery stays server-side. When PhilSMS is down, the `CONTACT_OTP_BACKUP_CODE` secret is accepted for any user (DEC-134), so it must be rotated after demos and unset once SMS delivery is reliable. |
| Admin verification review | `app/admin/verifications.tsx` | `verifications`, `verification_files`, `profiles` | P0 | Existing | Barangay admins land on a verification dashboard with queue filters, request metrics, submitted profile/file details, in-app image preview, logout, and approve/reject/return-for-correction actions through `AdminService`. It is one section of the Barangay Admin shell (DEC-070), alongside Reports, Users, public-photo review, and Settings, and keeps current `verifications` naming for MVP. |
| Home feed | `app/(tabs)/index.tsx`, Figma dashboard | `jobs`, `services`, `profiles`, `reviews`, `saved_items` | P0 | Partial | Home now loads real open jobs and active services from Supabase, preserves intent-based default filters, uses lightweight preference scoring plus mixed `For you` ordering, has a local discovery filter sheet for feed type, work mode, category, location preference, and sort, and exposes functional save toggles for visible feed cards. |
| Job posting and management | `app/create-job.tsx`, `app/create-job-preview.tsx`, `app/(tabs)/post.tsx`, `app/post/active.tsx` | `jobs`, `job_drafts` | P0 | Existing | Post is the primary owner surface for active posts, drafts, final posts, edit actions, lifecycle actions, and completed-job review entry. Owner job detail may link to the same edit flow. Profile may show history but does not own post management. |
| Job browsing | Home/search screens, job detail | `jobs` | P0 | Partial | Providers can view open jobs. Job details are task-first, keep poster trust metrics separate from job tags, and link to a safe public client profile that exposes only public-safe identity, activity, and active-job data. `explore` is legacy and should be replaced by Home/Search. |
| Provider browsing | Home/search screens, worker detail | `profiles`, `provider_profiles`, `services`, `credentials`, `reviews` | P0 | Partial | Clients can view providers. Worker details are person-first and separate identity/trust/skills/reviews/history from marketplace inventory such as active service listings and listing rates. `explore` is legacy and should be replaced by Home/Search. |
| Job interest messaging | Messages tab, job detail, feed cards | `conversations`, `messages`, `conversation_reads`, `jobs` | P0 | Existing | Job detail atomically creates or reuses one context conversation. Conversation detail supports text/image messages, quick prompts, canonical participant identity, per-user archive, report, and Mark Hired. |
| Hiring management | Messages tab, job history, post dashboard | `jobs`, `conversations` | P0 | Partial | Client can mark a conversation as hired; this updates conversation status and job accepted provider/status. |
| Search and filtering | Search screen, entered from Home | `jobs`, `services`, `profiles` | P0 | Partial | Search is no longer a bottom-navigation destination (DEC-121). It keeps its route, filters, taxonomy, and personalization, and is entered from the Home search bar, the Explore Services grid, and the Home feed-filter sheet, with a back affordance. Home uses the Find work / Hire help segmented control plus its own feed-filter sheet and preference scoring (DEC-122). |
| Ratings and feedback | Completed job detail, conversation details, public profiles, Post management | `reviews`, `jobs`, `conversations` | P1 | Existing | Reviews are reciprocal and immutable. After a completed hired job, the client may review the accepted worker and the worker may review the client once. Database RPCs derive the counterparty and enforce completion, hired participation, verification, no self-review, and no duplicates. |
| Reports/moderation | Report actions on job detail, Search results, and conversation details; `app/admin/reports.tsx`, `app/admin/photos.tsx`, `app/admin/users.tsx` | `reports`, `admin_moderation_actions`, `content_visibility` | P1 | Existing | Residents report jobs, listings, and conversations. Admins work the report queue (open, reviewing, received, resolved, dismissed), review users, and flag, hide, or clear public-facing photos with an audit trail (DEC-071). Account restriction and physical storage takedown remain deferred. |
| Basic messaging | Messages tab, `app/conversation/[conversationId].tsx` | `conversations`, `messages`, `conversation_reads`, private message storage | P0 | Existing | Real inbox, job/service conversations, text and private image messages, quick prompts, participant-scoped unread/archive state, canonical identity, context cards, details, and report are connected. Calls, push notifications, group chat, and per-message read receipts remain deferred. |
| Saved posts | Home/Search/detail cards, `app/saved.tsx`, Profile shortcut | `saved_items` | P1 | Existing | Verified users save individual job or service posts. The state is private, unique per user/post, optimistically updated with rollback, restored from Supabase, and browsable in a filterable Saved Posts destination with unavailable-post handling. |
| Notifications | Home header, Messages header, `app/notifications.tsx` | `notifications` | P1 | Partial | Basic in-app notification center with unread/read state for messages, verification decisions, completed hired jobs, and report status changes. Push delivery and preferences remain deferred. |
